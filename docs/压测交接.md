## 3. 压测脚本（已就绪，含全部修复）

**脚本**：`tmm.v11\stress_run.sh`（最新版，00:51）

### 3.1 核心参数（脚本头部可改）
| 参数 | 默认 | 说明 |
|---|---|---|
| `MEDIA_BUDGET` | 100 | 媒体深测总预算（项数）|

| `TH_*` | 见脚本 | K6 风格阈值（消息<3s/缩略图<2s/原图<5s/首段<3s/持续<8s/seek<8s/失败率<15%）|

### 3.2 命令行
```bash
# 完整压测（自动：频道抽样→消息加载→媒体预览→阈值判定→重合度检查）
bash stress_run.sh

# 只测频道消息加载（跳过媒体）
bash stress_run.sh --chats-only

# 复用已生成媒体集合（跳过阶段1频道加载）
bash stress_run.sh --media-only

# 固定随机种子（可复现）
bash stress_run.sh --seed 12345

# 复用已有频道抽样
bash stress_run.sh --keep-chats
```

### 3.3 已实现的核心逻辑
- **预算制分层抽样**：100 媒体按真实分布（~31% 图 / ~69% 视频）分层，均匀覆盖频道，每频道视频封顶
- **每轮强制重抽频道**：默认从 `/api/chats` 重新随机抽 15-20%（`stress_chats.txt` 存在也重抽，除非 `--keep-chats`）
- **事前重合度 ≤50%**：与 `stress_last.json` 对比，频道/媒体重合>50% 自动重抽（最多 10 次）
- **随机种子**：`--seed N` 固定可复现；缺省时间播种每轮独立（bash RANDOM + node 内联 LCG 双驱动）
- **K6 风格阈值判定**：阶段 3 自动输出 PASS/FAIL

## 4. 已知结论（前两轮压测发现，新对话可参考/复验）

### 4.1 视频随机进度跳转（seek）是核心瓶颈（已实锤）
第一轮 26 个视频数据：
| 指标 | 结果 |
|---|---|
| 首段 vfirst | P50 3.9s / **P95 24s**（慢）|
| 持续 vplay | P50 1.4s / **P95 27s** |
| **seek vseek** | P50 3ms ✅ / **P90 11s / P95 18s / 失败 9%** |
| seek 失败分布 | 20%-80% 各段都有 |

**根因**：seek 到未下载区域时，服务器实时向 Telegram 拉 chunk，RPC `context deadline exceeded`（`server/file_downloader.go:406`），请求挂起 30s+。用户拖进度条到随机位置经常卡死。

**初步修复方向**（最终报告需细化+判定是否值得改）：
- seek 到未缓存区域：优先从已缓存部分播放 + 后台异步拉取，不阻塞等待 RPC
- 或对 RPC 加更精细超时/重试

### 4.2 网络本身无问题
第一轮 `net_monitor.csv`：下载最高 3.4Mbps / 上传 4.7Mbps，**无骤降/抖动**——瓶颈在服务器→Telegram RPC 层，非本地网络。

### 4.3 消息加载/首段播放正常
stream 283/285 成功（99.3%），firstByte P50 2.5s。
