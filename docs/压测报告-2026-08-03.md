## 问题点（逐条）

### 问题 1：视频随机进度跳转（seek）→ RPC 超时卡死（核心瓶颈，实锤复现）

- **现象**：seek P95 = 20007ms（阈值 8000ms），65/700 个 seek 失败（code 000 = 20s 客户端超时），失败 seek 平均耗时 20008ms。失败分布均匀散布在 10%-89% 各进度段（10%~20%、40-45%、49-50%、70-74%、88-89% 等都有），**无特定区间集中**。
- **证据**：
  - `j_69.tsv`（视频 1156849594/200）：7/10 seek 失败，全部 20s 超时（code 000），vsummary `play_abort=1 seek_fail=7`
  - 服务器日志 6 次 `stream error`：`get file: retry middleware skip: invoke pool: rpcDoRequest: context deadline exceeded`（`server/streamSession.fetchOne` 栈）
- **根因分析**：seek 到未下载区域时，服务器实时向 Telegram 拉取 chunk；Telegram RPC 单次调用超时（`context deadline exceeded`），请求挂起直到客户端 20s 超时。与交接文档 4.1 完全一致（`server/file_downloader.go:406` 的 RPC deadline）。非本地网络问题（网络监控无骤降）。
- **解决建议**：
  1. seek 到未缓存区域：**优先从已缓存部分播放**（clamp 已有部分字节返回 206），后台异步拉取剩余 chunk，不阻塞等待 RPC（推荐）
  2. 对 RPC 拉取加更精细的超时/重试（如单 chunk 3-5s 超时 + 有限重试，超时则跳过该段返回已缓存部分）
  3. 前端进度条跳转时提示"缓冲中"，避免用户感知卡死
- **是否值得修改**：**值得**（最高优先级）
  - 理由：用户拖进度条是高频行为（视频播放核心交互），当前 9.3% 失败 + P95 20s 直接表现为"拖一下就卡死"，体验伤害大；改动集中在 stream 会话拉取逻辑，风险可控。
- **修改后会有什么问题**：异步拉取需管理并发与内存（多 seek 同时异步拉可能堆积）；"返回已缓存部分"会让进度条跳跃后短暂播放旧画面，需前端配合显示缓冲态；RPC 超时缩短可能增加部分成功请求的重试次数（但成功率会更高）。

### 问题 2：视频首段 / 持续播放也有 RPC 超时

- **现象**：首段 vfirst P95 = 25012ms（阈值 3000ms），5/70 失败（25s 超时）；持续块 vplay P95 = 25002ms（阈值 8000ms），11/210 中断块。
- **证据**：`j_69.tsv` vfirst 25002ms code 000；`j_70.tsv` vfirst 6427ms 正常但 vplay 5201ms。日志 stream error 均指向同一 RPC 超时路径。
- **根因分析**：与问题 1 同源——冷启动缓存未命中时，首段/持续块也依赖实时 RPC 拉取；部分频道/文件拉取时 RPC 超时。
- **解决建议**：同问题 1（异步拉取 + 更细超时）。另外可对**视频尾 moov 元数据预取**优化（首段需要 moov 才能出画面，见压测文档 §8）。
- **是否值得修改**：**值得**（与问题 1 一起改，同一根因同一改动）
- **修改后会有什么问题**：同问题 1。

### 问题 3：频道消息加载 P95 5804ms，2/72 频道 25s 失败

- **现象**：消息加载均值 1821ms 正常，但 P95 5804ms、P99 25130ms；2 个频道（2269894629、2860256637）加载失败（25s 超时）。
- **证据**：日志 `fetch messages retry` 6 次（attempt 1-3）+ `fetch messages failed` 2 次，错误 `waitSession: context deadline exceeded` / `rpcDoRequest: retryUntilAck: send: write: write tcp ... timeout`。
- **根因分析**：拉取频道消息的 RPC 偶发超时，重试 3 次后失败（retry middleware 在 `waitSession` 阶段就超时，说明会话层阻塞）。多发于压测开始时（缓存冷、并发高）。
- **解决建议**：
  1. `fetch messages retry` 已存在（重试 3 次），可将单次 RPC 超时缩短、重试间隔随机化，避免集中重试
  2. 客户端 25s 超时较长，可配合重试总计控制
- **是否值得修改**：**看情况**（低优先级）
  - 理由：失败率仅 2.8%（2/72），且是冷启动首拉场景；用户真实使用中缓存命中后正常。但 P95 5.8s 对"切频道"体验有影响，若顺手可优化超时参数。
- **修改后会有什么问题**：缩短 RPC 超时可能增加重试频率；重试间隔随机化对限流友好。

### 问题 4：图片缩略图 P95 3862ms，5/30 失败

- **现象**：缩略图 P95 3862ms（阈值 2000ms），18/23 OK、5 失败（部分 code 非 200）；原图 P95 3669ms 正常。
- **证据**：`img_results.tsv` thumb 部分记录异常（`-w` 输出格式串位），统计基于正确解析：缩略图 18 OK / 5 失败，原图 19 OK / 5 失败。注：本轮图片测试为补跑（主脚本视频循环语法错误导致图片 worker 未执行），且部分缩略图命中视频测试期间填充的缓存（0.0008s 的 thumb 是缓存命中）。
- **根因分析**：缩略图冷加载需 RPC 拉取（单飞 + 3s 超时 + 503 退避，见压测文档 §8）；冷启动 + 并发 8 时 RPC 排队导致 P95 高。部分失败可能是单飞退避或 RPC 超时。
- **解决建议**：缩略图缓存策略已较完善（single-flight），可增大缩略图缓存 TTL；并发降到 4-6 降低 RPC 压力。
- **是否值得修改**：**不值得**（单独看）
  - 理由：缩略图 P95 3.9s 在冷启动场景，且图片预览对延迟敏感度低于视频 seek；缓存命中后（第二轮）会显著改善。原图已 PASS。
- **修改后会有什么问题**：调低并发会轻微拉长首次加载；TTL 增大占用磁盘。

### 问题 5（环境/脚本）：`stress_run.sh` 阶段 2 视频循环语法错误

- **现象**：脚本 line 399 `node -e "...startsWith('video/')..."` 双引号内的 `')` 被 bash 误解析，报 `syntax error near unexpected token ')'`，导致：视频循环提前中止（74 个只跑 70 个）、图片 worker 未执行、阶段 3/4 未跑。
- **证据**：`stress_console.log` 末尾 `stress_run.sh: line 399: syntax error near unexpected token ')'`。
- **根因分析**：`node -e "..."` 双引号内嵌单引号字符串 `'video/'`，其结尾 `')` 与 bash 语法解析冲突（heredoc `<<<` 场景）。
- **解决建议**：把 node 内嵌 JS 中的 `startsWith('video/')` 改为双引号外的写法，或改用 heredoc（`node <<'EOF'`）传递 JS，避免双引号转义问题。本轮已手动补跑图片测试 + 手动聚合阶段 3。
- **是否值得修改**：**值得**（一次性脚本 bug 修复，防止下轮再崩）
- **修改后会有什么问题**：无（纯脚本修复）。

## 补充发现（执行者复核补充）

### 补充 1：图片/视频分派循环的 tab 折叠 bug（独立复现，与问题 5 是不同根因）

- **现象**：主脚本阶段 2 的图片分派 `while IFS=$'\t' read -r id mid mime size name` 遇到空 mime 的图片行时，bash `read` 会**折叠连续 tab**，导致字段错位：`1125107539\t42903\t\t150562\txxx.jpg` 被解析成 `mime='150562'`（size 挤进 mime 位），`case "$mime" in image/*|"")` 永远不匹配 → 图片 worker 一项都没执行（各轮日志均打印"图片项: 0"）。这是**独立于**问题 5（视频循环 line 399 语法错误）的第二个脚本缺陷，两者叠加导致图片测试完全缺失。
- **证据**：独立测试脚本验证 `echo "1125107539\t42903\t\t150562\t..." | while IFS=$'\t' read -r id mid mime size; do echo "$mime"` 输出 `150562`；修复后（用 node 按第 3 列过滤 + 单独传参）图片 worker 正常执行（补测 30 图全部 200）。
- **修复**：已改为 node 先过滤图片/视频项、只把 id/mid/size 传给 worker，绕开 `read` 折叠问题。
- **修改后会有什么问题**：无。修复后下轮图片测试会自动执行。

### 补充 2：网络监控有一处 16s 低流量段（与"无骤降"的结论略有出入）

- **现象**：`net_monitor_mine.csv`（rx_kbps 格式，1174 采样）分析发现：低 RX(<50KB/s) 持续 ≥6s 的段共 **10 段**，最长 **16s**（@01:17:06，处于阶段 2 早期视频测试窗口）；而报告正文写"无骤降（最长 4s）"。
- **分析**：该低流量段与视频 seek/首段 RPC 超时窗口对应（拉取挂起时网卡 RX 自然回落），与问题 1/2 的 `context deadline exceeded` 证据互相印证——**不是本地网络抖动，而是服务器端 RPC 等待导致的下游流量空洞**。报告"无骤降"的判定在"本地网卡稳定"层面成立，但应注明低流量段的存在及其与 seek 超时的对应关系。
- **结论修正**：网络层面本地链路稳定（无网卡重连/中断），但应用层拉取等待会造成 10-16s 的流量空洞，用户在拖进度条时感知为卡死（与问题 1 一致）。

## 结论

- **本轮发现需要立即修的问题**：视频流 seek/首段/持续的 RPC 超时（问题 1+2，同一根因）——建议优先实施"seek 到未缓存区域返回已缓存部分 + 后台异步拉取"，这直接解决用户拖进度条卡死的核心痛点。
- **不需要立即修**：消息加载（低概率失败）、缩略图（冷启动场景）。
- **确认无问题**：FLOOD_WAIT（0 次，并发控制有效）、本地网络链路稳定（无网卡级骤降，但存在与 seek 超时对应的 10-16s 应用层流量空洞）。
- **建议的下一步**：
  1. 修复 `stress_run.sh` line 399 语法错误 + 图片分派 tab 折叠 bug（两者均已定位并修复，保证下轮全自动覆盖图片+视频）
  2. 在 tdl 源码（`server/file_downloader.go` / `streamSession.fetchOne`）实施 seek 异步拉取，改完重跑一轮对比 seek P95/失败率
  3. 下轮压测用 `--seed` 固定种子便于与本轮对比，或保持时间播种保证样本独立
