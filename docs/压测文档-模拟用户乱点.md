# tmm 性能压测文档（模拟用户乱点行为）

> **给新对话/新 agent 的执行手册**：本文档描述如何对 tmm 进行一轮完整的性能压测——模拟用户随机乱点频道/消息/媒体，找出性能瓶颈、网络抖动、RPC 限制，并输出分析报告。
>
> 交付物：压测结果 + 分析报告（问题点、解决方案、是否值得改、改动影响）。

---

## 1. 背景与目标

tmm 是本地 Web 服务（`http://127.0.0.1:8080`），用户真实行为是：**频繁切换频道、滚动加载消息、点开媒体预览/播放**。压测要模拟这种"乱点"行为，回答：

1. **频道消息加载**是否卡顿（切换频道时等多久）？
2. **媒体预览**（图片缩略图 / 原图 / 视频流 / 持续播放 / 随机进度跳转）是否有性能瓶颈？
3. **网络流量**是否有骤降/抖动（服务器向 Telegram 拉取数据的中断）？
4. **RPC 抖动/限制**（Telegram 的 FLOOD_WAIT、限流）是否触发？
5. 每个问题**是否值得修**、修了有什么影响？

## 3. 压测参数设计（对应需求）

### 3.1 频道抽样（需求 1）
- 从 `/api/chats` 拿全部频道列表
- **随机抽取 15%-20%** 的频道（比如 50 个频道抽 8-10 个）
- 逐个点击（顺序访问）这些频道，测**消息加载速率**（`GET /api/chats/{id}/messages`）

### 3.2 媒体抽样（需求 2）
- 对每个抽样频道，**完整加载所有 msgid**（用 `offset_id` 分页翻到底，或加载足够多页覆盖媒体）
- 在完整 msgid 集合里**随机抽取 10%-20%** 的媒体消息做预览测试：
  - **图片**：缩略图加载（`/thumb`）、原图加载（`/file`）
  - **视频**：预览加载（`/stream` 首段）、**持续播放**（连续拉取多个 2MB 块）、**随机进度播放**（10%-90% 之间随机取 **10 个点**跳转，`Range: bytes=<pct>%`）
- 记录每个请求的耗时、大小、HTTP 状态码

### 3.3 网络/ RPC 监控（需求 3）
- **网络流量**：监控压测期间的网络收发字节，看是否有**骤降**（下载中断）或**抖动**（速率不稳定）
- **RPC 限制**：压测后翻服务器日志，搜关键词：
  - `FLOOD_WAIT` / `flood`（Telegram 限流）
  - `fetch messages retry`（消息拉取重试）
  - `stream error` / `thumb.*fail` / `context canceled`（流中断）
  - `rate limit` / `throttle`

### 3.4 抽样重合度控制（需求 4）
- **每次压测随机抽取的 (dialogid, msgid) 集合，与上一次压测的重合度不能超过 50%**
- 实现：压测前把上次的抽取集合写入 `stress_last.json`，本次抽取后对比，超过 50% 就重新抽样

### 3.5 报告输出（需求 5）
- 每次压测结束，输出分析报告，包含：问题点、原因分析、解决建议、**是否值得修改**（YAGNI 判断）、**修改后可能引入的问题**

## 4. 可执行压测脚本

> 脚本基于 `real_stress.sh` 增强，新增：媒体百分比抽样、完整 msgid 加载、视频随机进度点、重合度控制、报告生成。

### 4.1 准备：抽取频道 + 生成抽样集合

```bash
# 1) 拿频道列表
curl -s http://127.0.0.1:8080/api/chats > stress_chats_raw.json

# 2) 随机抽 15-20% 频道（示例：node 脚本）
node -e "
const fs=require('fs');
const d=JSON.parse(fs.readFileSync('stress_chats_raw.json','utf8'));
const chats=d.chats||[];
const n=Math.max(1,Math.round(chats.length*(0.15+Math.random()*0.05)));
const picked=[...chats].sort(()=>Math.random()-0.5).slice(0,n);
fs.writeFileSync('stress_chats.txt',picked.map(c=>c.id).join('\n'));
console.log('抽样频道数:',n,'/',chats.length,'= '+(n/chats.length*100).toFixed(1)+'%');
fs.writeFileSync('stress_chats_raw.json',JSON.stringify(picked));
"
```

### 4.2 主压测脚本 `stress_run.sh`

```bash
#!/usr/bin/env bash
# tmm 压测：乱点频道/消息/媒体 + 监控 + 重合度控制
set -u
BASE="http://127.0.0.1:8080"
LOG_BASE=$(wc -l < logs/server.log 2>/dev/null || echo 0)
TS=$(date +%s)
PERF_LOG="stress_report_$TS.log"
> "$PERF_LOG"

# --- 重合度控制：读上次抽取集合 ---
LAST="stress_last.json"
[ -f "$LAST" ] && LAST_KEYS=$(node -e "const d=JSON.parse(require('fs').readFileSync('$LAST','utf8'));process.stdout.write((d.keys||[]).join('\n'))")
THIS_KEYS=""

echo "=== tmm 压测开始 $TS ===" | tee -a "$PERF_LOG"
echo "日志基线: $LOG_BASE" | tee -a "$PERF_LOG"

# --- 阶段 0: 读抽样频道 ---
mapfile -t CHAT_IDS < stress_chats.txt
NCHATS=${#CHAT_IDS[@]}
echo "抽样频道数: $NCHATS" | tee -a "$PERF_LOG"

# 网络监控：后台采样 /proc/net/dev（Linux）或 netstat（Windows）
# （Windows 用 powershell Get-NetAdapterStatistics 采样）

TOTAL_MSG=0; TOTAL_MEDIA=0
THUMB_OK=0; THUMB_SLOW=0; THUMB_FAIL=0; THUMB_BYTES=0
FILE_OK=0; FILE_SLOW=0; FILE_FAIL=0
STREAM_OK=0; STREAM_SLOW=0; STREAM_FAIL=0; STREAM_BYTES=0

# --- 阶段 1: 逐个频道加载消息（乱点切频道）---
echo "=== 阶段 1: 频道消息加载 ===" | tee -a "$PERF_LOG"
for id in "${CHAT_IDS[@]}"; do
  # 随机 limit
  lim=$(( (RANDOM % 51) + 50 ))
  m_start=$(date +%s%N)
  # 完整加载所有 msgid（翻页直到 nextCursor 空或达上限）
  m_body=$(curl -s -m 20 "$BASE/api/chats/$id/messages?limit=$lim&media_only=1")
  m_ms=$(( ( $(date +%s%N) - m_start ) / 1000000 ))
  m_count=$(echo "$m_body" | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>{try{console.log((JSON.parse(d).messages||[]).filter(x=>x.hasMedia).length)}catch(e){console.log(0)}})")
  TOTAL_MSG=$((TOTAL_MSG + m_count))
  echo "频道 $id: 消息加载 ${m_ms}ms, ${m_count}媒体" | tee -a "$PERF_LOG"
done

# --- 阶段 2: 媒体抽样测试 ---
echo "=== 阶段 2: 媒体预览/播放 ===" | tee -a "$PERF_LOG"
# 每个频道从完整 msgid 随机抽 10-20% 媒体
for id in "${CHAT_IDS[@]}"; do
  # 拿完整 msgid 列表（翻页）
  FULL_IDS=$(curl -s "$BASE/api/chats/$id/messages?limit=100&media_only=1" | \
    node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>{const m=(JSON.parse(d).messages||[]).filter(x=>x.hasMedia);process.stdout.write(m.map(x=>x.id+' '+x.media.mime).join('\n'))})")
  # 随机抽 10-20%
  SAMPLE=$(echo "$FULL_IDS" | shuf --random-source=/dev/urandom | head -$(( $(echo "$FULL_IDS"|wc -l) * 15 / 100 + 1 )) )
  while read -r mid mime; do
    [ -z "$mid" ] && continue
    THIS_KEYS="$THIS_KEYS $id/$mid"
    # 图片：缩略图 + 原图
    if echo "$mime" | grep -q "^image/"; then
      t=$(curl -s -o /dev/null -w "%{time_total}|%{size_download}|%{http_code}" -m 15 "$BASE/api/media/$id/$mid/thumb")
      ...
    fi
    # 视频：首段 + 持续 + 10 个随机进度点
    if echo "$mime" | grep -q "^video/"; then
      ...
    fi
  done <<< "$SAMPLE"
done

# --- 阶段 3: 统计 + 重合度检查 + 报告 ---
echo "=== 阶段 3: 统计 ===" | tee -a "$PERF_LOG"
echo "总消息: $TOTAL_MSG 总媒体: $TOTAL_MEDIA" | tee -a "$PERF_LOG"
echo "缩略图 OK=$THUMB_OK 慢=$THUMB_SLOW 失败=$THUMB_FAIL" | tee -a "$PERF_LOG"
echo "原图 OK=$FILE_OK 慢=$FILE_SLOW 失败=$FILE_FAIL" | tee -a "$PERF_LOG"
echo "视频流 OK=$STREAM_OK 慢=$STREAM_SLOW 失败=$STREAM_FAIL" | tee -a "$PERF_LOG"

# 重合度
if [ -f "$LAST" ]; then
  OVERLAP=$(node -e "
    const cur=new Set('$THIS_KEYS'.trim().split(/\s+/));
    const prev=new Set('$LAST_KEYS'.trim().split(/\s+/));
    let hit=0; cur.forEach(k=>{if(prev.has(k))hit++});
    const pct=cur.size?hit/cur.size*100:0;
    console.log(pct.toFixed(1));
  ")
  echo "与上次抽取重合度: $OVERLAP% (要求 ≤50%)" | tee -a "$PERF_LOG"
  node -e "console.log('$OVERLAP' > 50 ? '❌ 超限，需重新抽样' : '✅ 达标')" | tee -a "$PERF_LOG"
fi
node -e "fs.writeFileSync('stress_last.json',JSON.stringify({ts:'$TS',keys:'$THIS_KEYS'.trim().split(/\s+/)}))"

# --- 阶段 4: 日志 RPC/网络分析 ---
echo "=== 阶段 4: 日志分析 ===" | tee -a "$PERF_LOG"
NEW_LOGS=$(sed -n "${LOG_BASE},\$p" logs/server.log 2>/dev/null)
echo "stream req: $(echo "$NEW_LOGS"|grep -c 'stream req')" | tee -a "$PERF_LOG"
echo "stream done: $(echo "$NEW_LOGS"|grep -c 'stream done')" | tee -a "$PERF_LOG"
echo "stream error: $(echo "$NEW_LOGS"|grep -c 'stream error')" | tee -a "$PERF_LOG"
echo "thumb fail: $(echo "$NEW_LOGS"|grep -c 'thumb.*fail')" | tee -a "$PERF_LOG"
echo "fetch retry: $(echo "$NEW_LOGS"|grep -c 'fetch messages retry')" | tee -a "$PERF_LOG"
echo "FLOOD/flood: $(echo "$NEW_LOGS"|grep -ic 'flood')" | tee -a "$PERF_LOG"
echo "context canceled: $(echo "$NEW_LOGS"|grep -c 'context canceled')" | tee -a "$PERF_LOG"

echo "=== 压测结束，报告见 stress_report_$TS.log ==="
```

> **注意**：上面是骨架脚本，`...` 处需补全（图片/视频的具体请求逻辑）。新对话应基于此骨架 + `real_stress.sh` 完整实现，跑通后验证数据合理。

## 5. 网络流量监控（需求 3）

### Windows 下用 PowerShell 采样

```powershell
# 压测期间每 2 秒采样一次网卡字节数，输出到 net_monitor.csv
$out = @()
$last = Get-NetAdapterStatistics | Where-Object {$_.Name -like "*Ethernet*" -or $_.Name -like "*Wi-Fi*"}
while ($true) {
  $now = Get-NetAdapterStatistics | Where-Object {$_.Name -like "*Ethernet*" -or $_.Name -like "*Wi-Fi*"}
  $rx = ($now | Measure-Object ReceivedBytes -Sum).Sum
  $tx = ($now | Measure-Object SentBytes -Sum).Sum
  $out += "$(Get-Date -Format 'HH:mm:ss'),$rx,$tx"
  Start-Sleep 2
  if ($out.Count -gt 600) { break }  # 20 分钟上限
}
$out | Set-Content net_monitor.csv
```

**分析**：把 `net_monitor.csv` 的 RX 列画出来，看有没有**骤降**（某段时间接近 0）或**抖动**（忽高忽低）。骤降往往对应：RPC 被限流、stream 会话中断、缓存未命中重新拉取。

### 服务器日志是第二证据
- `stream done` 的 `firstByte`/`cost` 字段：首字节延迟是否暴涨
- `fetch messages retry`：Telegram 拉取是否反复重试
- `context canceled`：流是否被中断

## 8. 已知参考（帮助判断瓶颈）

- **媒体流 clamp**：视频流每响应 2MB（`media.go` 的 `streamResponseChunks=4`），浏览器连续请求；压测模拟持续播放要连拉多个 2MB 块
- **缩略图单飞**：`handleMediaThumb` 有 single-flight + 3s 超时 + 503 退避；并发拉缩略图若缓存未命中会触发 Telegram RPC（~1.5-2s 每个）
- **消息分页**：`/api/chats/{id}/messages?offset_id=X&limit=N&media_only=1`，`nextCursor` 翻页；有内存 + 磁盘缓存（`cache/meta`）
- **缓存目录**：`cache/media`（原图）、`cache/meta`（消息列表）、`cache/preview`（视频流分片）
- **RPC 限流**：Telegram 单账号单 DC 约 30 并发 chunk 持续数秒触发 FLOOD_WAIT，`dl.go` 有 clamp（Limit×Threads=24 留缓冲）
- **性能敏感点**（历史上）：缩略图冷加载慢（RPC）、视频尾 moov 预取、`fetch messages retry`（网络抖动时）
